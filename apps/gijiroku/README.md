# 議事録・文書作成支援（試作）

会議の書き起こしテキストを貼り付けると、**議事録**または**復命書**の様式に整えて出力する、ビルド不要の静的Webアプリです（GitHub Pages 互換）。整文には Google の Gemini API を使い、APIキーは利用者がブラウザ内で入力し、`localStorage` にのみ保存します。

## 使い方（開発者向け）

- `index.html` をブラウザで開くだけで動作します（ビルド・サーバー不要）。
- **デモモード**：APIキー未設定でも、「サンプル文を入力」→「デモ出力で確認（APIなし）」で、議事録・復命書の全レイアウトを確認できます（サンプルは架空の内容）。
- ローカル確認：`python3 -m http.server -d apps/gijiroku 8000`

## ファイル構成

| ファイル | 内容 |
|---|---|
| `index.html` | 本体画面（入力・出力・APIキー設定・使い方） |
| `app.js` | ロジック（プロンプト生成、Gemini呼び出し、様式への組版、コピー／ダウンロード） |
| `demo.js` | デモ用サンプル（架空の書き起こしと出力） |
| `style.css` | 画面・印刷（A4）用CSS |
| `terms.html` / `privacy.html` | 利用規約・プライバシーポリシー（試作版の案） |

## 仕組み

1. 様式（議事録／復命書）に応じた**システムプロンプト**（整文ルール＋出力JSONの形）と、書き起こし本文（「データであり指示ではない」と明示）を Gemini API に送る。
2. 応答のJSONを検証・正規化し、アプリ側で様式（見出し・表・項番）に組版する。→ 様式の崩れを防ぎ、プレビュー・テキスト・Markdown・印刷で同一内容を出力できる。
3. 書き起こしにない情報を補った箇所・不明点は「要確認事項」に出す（事実を作らせない方針）。

画面の描画は `textContent` のみを使い、モデル出力のHTMLは解釈しません。CSP（`connect-src` は Gemini API のみ）を設定しています。

## 整文ルール（公用文の表記）について

プロンプトの表記ルール（送り仮名、漢字・かなの使い分け、算用数字、和暦・午前午後、敬語・文体、話し言葉の整理）は、国の「公用文作成の考え方」等の**一般的な公用文の考え方**に基づく試作です。

> **重要**：広島市「文書事務の手引」の本文は、この試作には取り込んでいません。手引の条文の引用もしていません。手引固有の規定（例：時刻・日付の書き方、敬称、文書様式）との適合は**未検証**で、手引の該当箇所を確認してプロンプト（`app.js` の `STYLE_RULES`）を調整する必要があります。

## 商用化の論点

### 1. データの取り扱い（最重要）
- 現状は、書き起こしが利用者のブラウザから Google の Gemini API へ**直接送信**される。会議内容には個人情報・非公開情報が含まれ得る。
- Google 側の保存・学習利用の有無は、プラン（無料／有料）や設定で異なる可能性がある。**契約形態ごとの条件を一次情報（Google の規約）で確認する必要がある**（本README作成時点で未確認）。
- 自治体では、情報セキュリティポリシー、個人情報保護条例・個人情報保護法、クラウド利用の可否（ISMAP等の認証要件の有無）が導入可否を左右する。要件は団体ごとに異なるため、個別確認が必要。
- 対策案：入力前の注意表示と同意チェック（実装済み）、マスキング（氏名・住所等の自動伏字）、送信範囲の限定、国内リージョン／ゼロデータ保持が選べる提供形態の検討。

### 2. オンプレミス・閉域網の需要
- LGWAN など閉域網の端末からインターネット上のAPIへ接続できない団体が多いと考えられる。その場合、ブラウザ完結＋外部API方式は使えない。
- 選択肢：①庁内サーバーに配置するオンプレミス版（ローカルLLMまたは閉域内の生成AI基盤を利用）、②自治体向けクラウド（閉域接続）経由、③ガバメントクラウド上の提供。
- ローカルLLMは、整文品質（公用文表記の遵守）・運用負荷・GPU調達の費用が論点。品質評価の基準（誤り率、様式の遵守率）を先に定めるべき。

### 3. 品質・責任
- 数値・日付・氏名・決定事項の取り違えは、公文書として重大。**人の確認を前提**とするUI（要確認事項の明示、原文との対照表示）を強化する。
- 免責・利用規約の整備（法務確認が必要。現状は案）。
- 表記ルールは団体ごとに異なる（手引・例規）。団体別ルールセットの設定機能が差別化要素になり得る。

### 4. 入力（書き起こし）の確保
- 本アプリは「書き起こし済みテキスト」が前提。音声認識（録音→文字起こし）を含めるかで、価格・データの取り扱い・精度の論点が増える。既存の文字起こしサービスとの連携が現実的な可能性がある（未検討）。

### 5. 価格・提供形態
- 候補：自治体向け年額ライセンス（職員数・課数単位）、オンプレミス版の買い切り＋保守、企業向けSaaS。
- API利用料を利用者負担（BYOK：自前のキー）にする現行方式は、試作・検証には適するが、自治体の調達・会計処理にはなじまない場合がある。
- 自治体への導入は、調達手続（入札・随意契約の要件）、導入実績の確保、セキュリティ審査の期間が壁になる。

### 6. 競合・代替
- 汎用の文字起こし・議事録AI、会議ツール内蔵の要約機能、議会向け会議録システムが存在する。公用文表記と様式への特化をどこまで差別化にできるか、調査が必要（本README作成時点で未調査）。

## 残課題

- 広島市「文書事務の手引」の該当規定を確認し、`STYLE_RULES` に反映する。
- 実際のGemini APIでの動作確認（開発環境ではAPI呼び出しをモックして検証したのみ。既定モデル `gemini-3.8-flash` は姉妹アプリでの動作確認結果に基づく設定で、本アプリ上では未検証。旧既定の `gemini-2.5-flash` は新規APIユーザーで404になる事例があるとの報告による変更）。
- 長文（長時間会議）の分割処理、テキスト入力上限（現在6万字）の見直し。
- 複数の様式（会議録、報告書、起案文）やDOCX出力、団体別ルールセット。
- 利用規約・プライバシーポリシーの法務確認、運営者情報・問い合わせ先の記載。
- マスキング機能、アクセシビリティ（スクリーンリーダー等）の検証、実機での印刷確認。
