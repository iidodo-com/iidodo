# 手元資料LLM処理（local-doc-llm）

PC内のローカルLLM（Foundry Local / Ollama などOpenAI互換）**だけ**に接続して、手元の `.txt` / `.md` / `.pdf` を要約・抽出・整文・Q&Aする静的Webアプリ。
想定環境: Snapdragon X Plus / Windows 11 ARM64 / メモリ16GB。

## 外部送信しない設計
- ライブラリは同梱（`vendor/pdfjs` = pdfjs-dist 4.10.38、Apache-2.0。CDN・外部フォント・外部スクリプトなし）。
- 接続先は loopback（`localhost` / `127.x.x.x`）のみ。`lib/core.js` の `callChat` / `listModels` は、それ以外のURLなら **fetch を呼ぶ前に拒否**（単体テストで検証）。
- さらに CSP（`index.html`）で `connect-src` を同一オリジン＋localhost/127.0.0.1 に限定。
- APIキー入力欄なし（`Authorization` ヘッダも送らない）。入力文書は保存しない（localStorage には URL・モデル名等の設定値のみ）。
- 注意: CSP は `http://[::1]` を表現できないため、IPv6 `::1` 直指定はブラウザ側でブロックされます（`localhost` を使ってください）。

## 起動方法（PC側）
Node.js（Windows ARM64 版可、v18以上想定。開発時は v22 で確認）が必要です。ES Modules / PDF worker は `file://` では動かないため、付属の小さなローカルサーバー経由で開きます。

```bash
cd apps/local-doc-llm
node serve.mjs            # → http://127.0.0.1:8787/
```
Windows ではエクスプローラーから `start.bat` をダブルクリックでも可（サーバー起動＋ブラウザ表示）。ブラウザは最新の Edge / Chrome（pdf.js 4.x が必要とする機能のため）。

### 接続先の設定
| LLM | ベースURL | 備考 |
|---|---|---|
| Ollama | `http://localhost:11434` | 自動で `/v1` を補います。モデル名は `ollama list` の名前。 |
| Foundry Local | `http://localhost:<ポート>/v1` | ポートは起動ごとに変わることがあります（`foundry service status` 等で確認）。モデルIDは「接続テスト」で表示される一覧から選べます。 |

初期モデル名は `qwen2.5-7b-instruct`。**「コンテキスト上限」は、モデルに実際に設定されたコンテキスト長以下**にしてください（初期値 8192）。チャンク分割の基準になります。

### CORS で接続できない場合
ブラウザから別ポートのLLMを呼ぶため、サーバー側がCORSを許可していないと「接続できませんでした」になります。
- Ollama: 既定で localhost 系オリジンは許可される想定ですが、環境によっては `OLLAMA_ORIGINS` の設定が必要です（要実機確認）。
- 回避策（実装済み）: 付属サーバーで中継します。
  ```bash
  node serve.mjs --target http://localhost:<LLMのポート>
  ```
  アプリのベースURLを `http://127.0.0.1:8787/llm/v1` にします（`--target` は loopback のみ指定可）。

### 実機なしで画面を試す
```bash
node test/mock-server.mjs --port 8799    # モックLLM（http://127.0.0.1:8799/v1）
node serve.mjs
```

## 使い方
1. ベースURL・モデル名を入れて「接続テスト」（`/models` → 失敗時は最小チャット呼び出しで確認。失敗理由を表示）。
2. ファイルをドロップ（複数可。txt は UTF-8、失敗時 Shift_JIS で読み込み）。
3. 処理を選択（要約 短め/詳しめ、要点抽出、決定事項・ToDo抽出、整文、複数文書Q&A）。
4. 「送信内容を確認する」→ 実際に送るメッセージ全文と、個人情報らしいパターン（メール・電話・郵便番号・7桁以上の数字列）の検出結果を表示。「マスキングしてから送る」（初期ON）で `[EMAIL_1]` 等に置換。マスクOFFで検出ありの場合は送信前に確認ダイアログ。
5. 「確認した内容で送信して実行」。結果はコピー／`.md` ダウンロード。「元に戻して表示」で、手元の表示だけプレースホルダを復元。

## 長文の扱い
- 推定トークン（CJK=1.0/字、その他=0.35/字の保守的な見積り）で、`コンテキスト上限 − 最大出力 − プロンプト − 余裕` ×0.9 を1チャンクの予算にして、段落→行→文→文字の順で分割（内容欠落なし）。
- 全文が1チャンクに収まれば1回で処理。超える場合は map（各チャンク）→ reduce（統合）。統合入力が予算を超える場合は階層的に中間統合（最大8段）。統合しきれない場合は部分結果を連結して警告表示。
- 整文は各チャンクを独立に処理して連結（統合なし）。Q&A は各チャンクから関連記述を抜き出し→統合。LLM呼び出しは直列。
- プレビューには第1段階のリクエストのみ表示（統合入力は第1段階の出力から作られるため事前に見えません）。呼び出し回数は概算。

## テスト
```bash
node test/run-all.mjs     # unit + e2e（e2e は Playwright/Chromium が必要）
```
- `test/mock-server.mjs`: OpenAI互換モック（/v1/models, /v1/chat/completions、ctx超過400・500・遅延を再現）。
- `test/unit.test.mjs`: URL正規化・外部拒否、チャンク分割、PII検出/マスク、リクエスト形式、map-reduce、エラー分類、静的サーバー。
- `test/e2e.test.mjs`: Chromium でUIを通しで操作（PDF抽出、プレビュー、マスク、停止時エラー、外部通信ゼロ）。

## 作業ログ・自己テスト結果（2026-11-06 実施、Linux上、Node v22.23.4 / Playwright同梱Chromium）
結果: **41件中 41件 PASS / 0件 FAIL**（unit 28件 + e2e 13件）。`serve.mjs --target` の中継は上記の手動 curl で `/models` と `chat/completions` の往復を1回ずつ確認（自動テストには未組込み）。

確認できたこと（モックに対して）:
- リクエスト形式: `POST /v1/chat/completions`、`model` / `messages(system,user)` / `stream:false` / `max_tokens` / `Authorization` なし。
- チャンク分割: 全チャンクが予算内、内容欠落なし、サロゲートペア安全、長文でモックの文脈上限（400）に1件も当たらない。階層統合も動作。
- エンドポイント停止時: 接続テスト・実行の両方で原因（未起動／URL・ポート／CORS）を示すエラー表示。500・コンテキスト超過・モデル名違い(404)・タイムアウト・中止も原因つき表示。
- マスキング: モックが受信した全リクエストに個人情報（メール・電話）が含まれない／質問文もマスク／復元表示。
- 外部通信ゼロ: ブラウザが発行した全リクエストが 127.0.0.1/localhost 宛（pdf.js worker は同梱ファイル）。外部URL指定は fetch 前に拒否。
- 自己テスト中に発見・修正: CSP の `http://[::1]:*` がChromeで無効な書式だったため削除。
