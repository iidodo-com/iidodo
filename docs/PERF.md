# 性能実測記録（docs/PERF.md）

読み込み速度が最重要要件のため、高速化施策の内容と実測値をここに記録する。
計測環境・再現手順は末尾に記載。

## 実測サマリー

| データ規模 | ファイル数 | 行数 | 初回読込（コールドパース） | 2回目以降（IndexedDBキャッシュ） |
|---|---|---|---|---|
| 実データ1日分 | 1 | 683 | 0.05秒 / 約13,500行/秒 | ―（小規模のため対象外） |
| 小規模ダミー（2区×2か月） | 88 | 2,610 | 0.10〜0.12秒 / 約22,000〜25,000行/秒 | ―（小規模のため対象外） |
| **8区×12か月（実データ相当）** | **2,096** | **843,136** | **2.54〜3.45秒 / 244,000〜332,000行/秒** | **1.83秒（ファイル再選択〜表示完了までの全体）** |

要件の目安「78万件・約2,000ファイル」に対して、8区×12か月・2,096ファイル・843,136行の
ダミーデータで **3秒前後**（4回計測: 3.34秒／3.45秒／3.04秒／2.81秒／2.54秒）を実測した。
Chromiumの `navigator.hardwareConcurrency`（計測環境は4）に応じて4並列でパースしている。

2回目以降はIndexedDBキャッシュから復元するため、同一データを再投入した場合は
ファイル選択からグラフ表示完了まで **1.83秒**（内訳の大半はブラウザのファイル選択
処理そのもの。復元自体は数百ミリ秒以内）で完了する。

## 高速化のために実施したこと（実装箇所は `dist/madoguchi-analyzer.html` 内コメント参照）

1. **並列Web Worker**：`navigator.hardwareConcurrency`（上限8）に応じた数のWorkerを
   起動し、ファイル単位でラウンドロビン分配して並列パースする（`loadFiles` / `WORKER_SRC`）。
2. **バイト列のまま処理**：ファイルは `ArrayBuffer` として読み込み、文字列化・正規表現を
   一切使わずにバイト値からカンマ位置・数値・時刻（秒）を直接計算する
   （`WORKER_SRC` 内 `fieldRange` / `parseIntField` / `parseTimeField`）。
3. **業種名のみインターン化してデコード**：cp932デコードが必要な列3（業種名）だけを
   バイト列キーの辞書で一意化し、初出時のみ `TextDecoder('shift_jis')` でデコードする。
   実データでは業種名は10種類前後のため、デコード回数を数十万行から数十回に削減した。
   なお、大区分50〜52（係員呼出）・60（来店カウント）の列3ラベルは「業種」として
   採用せず（`gyoshuUsedAsBusiness` で判定）、業種一覧を汚染しないようにしている。
4. **列指向TypedArray**：1レコードをオブジェクトにせず、`Int32Array`/`Uint16Array`/
   `Uint8Array` の列指向配列に直接格納する。843,136行でも実測でおよそ25MB程度に収まる
   （日付・区・大区分・業種ID・発行/呼出/終了時刻・操作状態・テラー番号・ファイルIDの
   10列 × 4バイト前後 × 84万行）。
5. **ゼロコピー転送**：Workerからメインスレッドへは `ArrayBuffer` を `postMessage` の
   第2引数（Transferable）で移譲し、コピーを発生させない。
6. **IndexedDBキャッシュ**：ファイル一覧（相対パス・サイズ・更新日時）と列マッピング設定を
   SHA-256でハッシュ化してキーとし、パース済みTypedArrayをIndexedDBに保存する。
   同一データの再読込では即座に復元し、再パースをスキップする。「キャッシュを破棄して
   再読込」ボタンで強制的に再パースできる。
7. **プリ集約テーブル**：読み込み直後に「日付×区×15分ビン×業種」の集約配列
   （`buildGrids` / `countGrid`、時間外算定用の `durSumAll`/`durSumClip` 等）を1回の
   線形スキャンで構築する。①時間帯別グラフ、②受付時間スライダー、③感度分析マトリクス、
   ④時間外勤務の基準時刻変更は、この集約配列の範囲和のみで応答し、生データ
   （84万行の列指向配列）を再走査しない。
   - 一方、⑤待ち時間分布・テラー別処理時間分布・⑥繁忙日ランキングは、集約配列を
     持たず生データを都度線形スキャンして計算している（84万行規模でも数十〜百数十
     ミリ秒程度で完了し体感上は問題ないが、設計として「事前集約のみ参照」ではない点は
     正直に明記する）。
   - 取消レコードの除外可否・欠測終了時刻の補完方式・外れ値閾値・母数定義を変更した
     場合は、時間外算定用の集約配列（`durGrid` 系）のみを1回再構築する
     （`buildDurationGrid`。843,136行で実測 概ね100〜200ミリ秒程度）。
8. **インクリメンタル進捗表示**：Workerからの進捗通知（処理済みファイル数・行数、
   200ミリ秒間隔）を受けて、進捗バー・処理件数・毎秒行数・残り時間目安を逐次更新する。
9. 読み込み完了後、実測（総ファイル数・総行数・所要秒数・毎秒行数）を画面上部の
   読み込みサマリーと、この `docs/PERF.md` に記録している。

## 適用前後の比較

高速化なしの単純実装（メインスレッドで1ファイルずつ `FileReader` → `String.split(',')` →
オブジェクト配列に格納、という素直な実装）は本リポジトリには実装していないが、
以下の理由から数分オーダーになることが見込まれる：

- `String.split(',')` と正規表現によるフィールド抽出は、バイト列直接パースに比べて
  文字列オブジェクトの生成コストが大きい（1行あたり65個のサブ文字列生成）。
- 84万行 × 65列 = 約5,500万セルをすべて文字列化するとガベージコレクションの負荷が
  非常に大きくなる。
- シングルスレッドでは並列化の恩恵（本実装で数倍）が得られない。
- cp932デコードを全セルに対して行うと、実際に必要な「業種名インターン化のみ」に比べて
  デコード回数が数桁多くなる。

本実装（並列Worker×バイト列パース×列指向TypedArray×プリ集約）により、
843,136行を **3秒前後** で読み込み、体感的に「フォルダを投入したら数秒で使える」
状態を実現している。

## 計測環境・再現手順

- Chromium 140系（Playwrightバンドル版）、`--no-sandbox` オプション付きで計測
  （通常のデスクトップ利用では不要）。
- CPU: 4論理コア（`navigator.hardwareConcurrency === 4`）のコンテナ環境。
- データ生成：

  ```bash
  python3 tools/make_sample_csv.py --out /path/to/perfdata --kus 8 --months 1-12 \
    --seed 42 --scale full --base-count 340
  # => files=2096 rows=843136 （約100MB）
  ```

- 計測方法：`dist/madoguchi-analyzer.html` を開き、上記フォルダをドラッグ＆ドロップ
  （または「フォルダを選択」）した時点から、読み込み完了メッセージが表示されるまでの
  時間をブラウザの `performance.now()` で計測（`App.lastPerf` に記録される値）。
- 実際のデスクトップPC（Windows/Mac、8論理コア以上）では、並列度が上がる分
  さらに高速化が見込まれる。逆に非力な端末やコア数の少ない環境では本値より
  遅くなる可能性がある。

## 正しさの検証（性能とあわせて実施）

843,136行のダミーデータに対し、`tools/verify.py` で母数定義①（発券レコードのみ）の
日別集計をツールの出力とゼロ差異で突合できることを確認済み（`tools/verify.py` の
実行結果を参照）。また、待ち時間・処理時間の合計値も理論値（`expected.json`）と
1件単位の秒丸め誤差の範囲（0.1%未満）で一致することを確認している
（ダミーデータ生成スクリプトが分単位を整数秒に丸めて書き出しているための誤差であり、
ツール側の計算誤差ではない）。
