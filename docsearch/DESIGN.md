# 設計メモ

## DB（index.db）
```
meta(key, value)                      スキーマ版、最終更新、初回メッセージ表示済みフラグ
files(id, root, relpath, ext, size, mtime_ns, status[ok/error/excluded], sig, indexed_at, chunk_count, truncated)
issues(file_id, kind, location, detail)   対象外・エラー・テキスト抽出不可・数式キャッシュなし・セル上限 の一覧用
chunks(id, file_id, location, text)       場所ごとの正規化済み本文
chunks_fts  FTS5(text, content='chunks', content_rowid='id', tokenize='trigram')   外部コンテンツ方式（本文は chunks に1回だけ保存）
```
- 外部コンテンツ方式のため、削除・更新時は、chunks を消す前に `INSERT INTO chunks_fts(chunks_fts, rowid, text) VALUES('delete', …)` で索引から外す（`db.delete_file`）。整合性は `integrity-check`（rank=1）で確認する。
- `sig` は抽出結果に影響する設定（セル上限など）の署名。変わったら全ファイルを再処理する。

## スニペットと本文の保存範囲
スニペットを作るには、場所ごとの本文が必要（保存しないと、表示のたびに元ファイルを再読込することになり、移動・削除されると表示できない）。
保存するのは**正規化後のプレーンテキストだけ**（書式・画像・メタデータは保存しない）。このため、スニペットは正規化後の文字（㈱→(株) 等）で表示される。
原文と正規化後の2系統を持つとDBが約2倍になるため、正規化後のみとした。

## 検索
- 検索語は NFKC・小文字化・空白整理（登録時と同じ `normalize`）。3文字以上は FTS5 の `"語"`（フレーズ）、3文字未満は `LIKE '%語%' ESCAPE '\'`。
- **場所単位（scope=place）**: 1つの場所が全条件を満たすものを列挙。bm25 は3文字以上の語の AND 検索に対する値。
- **ファイル単位（scope=file、既定）**:
  - 該当判定: 各語がファイルのどこかの場所にある。除外語は、どこかの場所にあればファイルごと除外。3文字未満の語は、3文字以上の語で絞った候補のファイルだけを LIKE で走査。
  - 関連度順: ファイルごとに、3文字以上の語を OR で FTS 検索した各場所の bm25 の最小値（最良）の昇順。同点は更新日の新しい順。
  - 更新日順: 更新日の新しい順、同じなら相対パス順。
  - スニペットの場所: 検索語を最も多く含む場所 → bm25 が良い場所 → ファイル内で先頭の場所、の順で選ぶ。該当場所の数も表示する。
- 3文字以上の語が1つもない検索は bm25 を計算できないため、更新日順にして通知する。

## 取り込みの処理の流れ
1. すべての roots の存在を確認（1つでも到達できなければ、何も変更せず中止）
2. 走査（リンク・ジャンクションは辿らない）。除外パターン、旧形式、サイズ超過、リンク、走査エラーを分類
3. 消えたファイルの削除を反映（読めなかったフォルダ配下は残す。半数超の削除は安全装置で止める）
4. 対象外・走査エラーの行を書き直す（ファイルは読まない）
5. 対象ファイルのうち、パス・サイズ・更新日時・sig が同じもの（エラー済みを含む）は飛ばし、残りを1ファイル＝1トランザクションで処理
6. 抽出: 読み取り（rb）→ BytesIO → 各ライブラリ。失敗は種別つきで記録して次へ

## 開く動作
既定は、OSの一時フォルダに読み取り専用のコピーを作って開く。終了時（atexit）と次回起動時に削除。
